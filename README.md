# Multi-Tenant SaaS Platform

![CI](https://github.com/Sindhupadmaja/Multitenant-Saas-platform/actions/workflows/ci.yml/badge.svg)

A production-shaped multi-tenant SaaS backend: organizations (tenants) with
role-based membership, tenant-isolated resources, usage-based billing
generated by a real background job, Redis caching, structured observability,
and a versioned API. It uses typed errors, manual dependency injection, and
real-database integration testing, and treats **multi-tenancy as a
first-class security boundary**, with a real job queue, real caching, and
real metrics.

## The central claim, proven, not asserted

```bash
npm test
```

`tests/integration/tenantIsolation.test.ts` is this project's centerpiece,
the same way the concurrency test was for the Service Booking Platform
project. It proves, against real PostgreSQL:

- A project created in organization A is **never** returned when listing
  organization B's projects.
- Fetching org A's project by ID while authenticated with org B's context
  returns **404**, not 403 — indistinguishable from "doesn't exist," so an
  attacker learns nothing about what *does* exist in another tenant.
- A user who is a genuine member of org B **cannot** access org A by simply
  sending org A's real, valid organization ID in the header — membership is
  checked, not just "is this a real org."
- The **same user** can simultaneously be `owner` in one organization and a
  plain `member` in another, with RBAC enforcing the right permissions in
  each context independently.

Full suite: **34 tests, all passing, all against real infrastructure** —
PostgreSQL, Redis, and a genuinely running BullMQ worker, not mocks.

## How tenant isolation actually works

Two things, both required, neither sufficient alone:

1. **`tenantMiddleware.ts`** reads `X-Organization-Id`, looks up the
   `(organization_id, user_id)` row in `memberships`, and only then sets
   `req.organizationId`. No membership row → 403, deliberately the *same*
   response whether the organization exists and the user just isn't in it,
   or the organization doesn't exist at all — a 404 here would itself leak
   information across the tenant boundary.
2. **Every repository method that touches tenant data takes
   `organizationId` as a mandatory parameter and bakes it into the query**
   (`ProjectsRepository.listForOrganization`, `getById`'s explicit
   `organization_id` check even after fetching by primary key). A route
   handler cannot query "all projects" and filter client-side — the
   filter has to be in the SQL, because nothing lower in the stack accepts
   an unscoped call.

## Everything else in this project, briefly

- **RBAC is per-tenant, not global.** There's no `user.role` column at
  all — role lives entirely on the `memberships` row, which is exactly
  what lets one person be an owner of their own org and a mere member of a
  client's org at the same time (tested directly).
- **Caching is real Redis, cache-aside, with immediate invalidation.**
  `GET /api/v1/projects` sets `X-Cache: HIT` or `MISS` so cache behavior is
  directly observable, not just trusted. A write invalidates the relevant
  key immediately rather than waiting out the 30s TTL — verified in
  `tests/integration/caching.test.ts`, including that two different tenants
  never share a cache entry (a cache-key collision would itself be a
  tenant-isolation bug hiding in a different layer).
- **Invoice generation is a real background job**, not a stub. The route
  enqueues to BullMQ and returns `202 Accepted` immediately; a separate
  worker process (`src/jobs/worker.ts`, its own Docker Compose service)
  picks it up, aggregates `usage_events`, and writes the `invoices` row.
  Tests wait on the actual job via `job.waitUntilFinished()` — the same
  mechanism a real client polling for completion would use.
- **Billing pricing is a documented constant**, not hidden arithmetic —
  `billing.service.ts`'s `BASE_FEE_CENTS` / `PRICE_PER_EVENT_CENTS`, the
  same "one clearly-labeled place, not scattered magic numbers" approach as
  the cancellation policy in the Service Booking Platform project.
- **Observability is real, not a checklist item.** `GET /metrics` returns
  genuine Prometheus exposition-format text (`prom-client`) that an actual
  Prometheus server could scrape as-is — tested against the real text
  format, not just a 200 status. Every request gets a correlation ID
  (generated or reused from an incoming `X-Request-Id`), echoed on the
  response and included in every error body.
- **API versioning is demonstrated, not just claimed.** `/api/v1/projects`
  and `/api/v2/projects` both work, share the exact same `ProjectsService`
  underneath, and return genuinely different response shapes (`{items}` vs
  `{data, meta}`) — proof the versions can evolve independently.

## Two real bugs caught during development (left visible, not hidden)

- BullMQ requires `maxRetriesPerRequest: null` on its Redis connection
  specifically, different from the cache layer's ioredis client -- using the
  wrong connection config for the queue silently breaks blocking commands.
  Documented directly in `jobs/connection.ts`.
- Inserting a **JS array** into a `jsonb` column (`invoices.line_items`)
  failed at the Postgres driver level ("invalid input syntax for type
  json") even though inserting a **plain object** into a jsonb column
  (`audit_logs.metadata`) worked fine — confirmed by testing both forms
  directly against real Postgres before fixing it. See
  `invoices.repository.ts`'s comment for the isolated repro.

## Setup

```bash
git clone <this-repo>
cd multitenant-saas-platform
npm install
cp .env.example .env    # edit JWT_SECRET
```

### Run with Docker Compose (API + worker + real Postgres + real Redis)

```bash
docker compose up --build
```

### Run locally (requires your own PostgreSQL + Redis)

```bash
createdb saas_platform
createdb saas_platform_test   # for tests
npm run migrate
npm run dev          # API, in one terminal
npm run dev:worker   # worker, in another
```

### Run the tests

```bash
npm test              # 34 tests -- requires reachable Postgres AND Redis
npm run test:coverage # same, with coverage (86.3% statements)
```

## API reference

| Endpoint | Auth | Description |
|---|---|---|
| `POST /api/v1/auth/register` | no | `{name, email, password}` → `{user, token}` |
| `POST /api/v1/auth/login` | no | `{email, password}` → `{user, token}` |
| `POST /api/v1/organizations` | yes | `{name, slug}` → creates an org, creator becomes `owner` |
| `GET /api/v1/organizations/mine` | yes | Organizations you belong to, with your role in each |
| `GET /api/v1/organizations/members` | yes + tenant | List members of the org in `X-Organization-Id` |
| `POST /api/v1/organizations/members` | owner/admin | `{email, role}` — add a member |
| `POST /api/v1/projects` | yes + tenant | Create a project (also records billable usage) |
| `GET /api/v1/projects` | yes + tenant | List, cached (`X-Cache: HIT`/`MISS`) |
| `GET /api/v1/projects/:id` | yes + tenant | 404s for another tenant's project |
| `DELETE /api/v1/projects/:id` | yes + tenant | Creator, admin, or owner only |
| `POST /api/v1/billing/invoices/generate` | owner/admin | `{periodStart, periodEnd}` → `202` + `jobId` |
| `GET /api/v1/billing/invoices` | yes + tenant | List generated invoices |
| `GET /api/v2/projects` | yes + tenant | Same data, `{data, meta}` shape |
| `GET /health`, `GET /metrics` | no | Liveness, Prometheus metrics |

"yes + tenant" routes require both `Authorization: Bearer <token>` and
`X-Organization-Id: <id>`.
